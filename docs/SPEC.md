# プロ野球 優勝確率・優勝決定日予測サイト 仕様書

## 1. 概要

NPB セ・パ両リーグの**優勝確率**と**優勝が決まる日**を毎日計算して公開する静的サイト。

報道が出すマジックナンバーは「最悪の場合あと何勝必要か」という数字でしかなく、「実際にいつ決まりそうか」「今どのくらいの確率で優勝するか」には答えていない。そこを埋めるのがこのサイトの狙い。

出すもの:

- 優勝確率 / CS進出確率（3位以内） / 最終順位の確率分布 / 予想最終成績
- **優勝決定日の確率分布**（このサイトの目玉）
- マジックナンバー（報道と同じ慣用値と、規定に忠実な厳密値の両方）
- 自力優勝の可否と、数学的敗退の厳密判定
- 「もしも」シミュレーター（ブラウザ内で条件を変えて再計算）

内容は1日1回しか変わらず、全ユーザーに同じものを見せる。したがって**実行時サーバーを持たない**。GitHub Actions が毎晩スクレイプ・計算・ビルドし、静的ファイルとして配信する。

### 選定理由

**なぜ Astro か。** このアプリの性質は「日次更新の静的コンテンツ ＋ 1画面だけクライアント計算」の一点に尽きる。SvelteKit や Next.js を静的アダプタで使うこともできるが、あれらは SSR・API ルートという実行時サーバーを構成の中心に据えたフレームワークで、ここでは要らない部品が主役になる。加えて全ページがハイドレートされるため、**JS 0KB のページを作れない**。実測で、シミュレーター以外の16ページは `<script>` タグが1つも出ていない。

**なぜ Spring Boot ではないか。** 計算エンジンがサーバー側に固定されてしまい、ブラウザで対話的に再計算する「もしも」シミュレーターと構造的に噛み合わない。データ量的にも JPA/DB は過剰。

**なぜ計算エンジンを素の TS パッケージにするか。** ビルド時（Node）とブラウザ（Web Worker）で**まったく同じコードを走らせる**ため。二重実装を作らないことが、数字の整合性を保つうえで一番効く。

**なぜ DB を使わないか。** 1シーズンは約860試合しかなく、`games.json` で152KB。Git が履歴・差分・ロールバックを兼ねてくれるうえ、日次スナップショットがそのまま「予測の当たり外れ」の検証データになる。SQLite を置くと運用対象が増えるだけで、得るものがない。

## 4. データモデル

### 4-1. `Game`（`data/<year>/games.json`）

| カラム                    | 型                                      | 説明                                                                 |
| ------------------------- | --------------------------------------- | -------------------------------------------------------------------- |
| `date`                    | `string`                                | `YYYY-MM-DD`                                                         |
| `home` / `away`           | `TeamId`                                | npb.jp の試合URLで使われているコード（`g` `t` `db` …）をそのまま採用 |
| `homeScore` / `awayScore` | `number \| null`                        | `status` が `final` のときのみ入る                                   |
| `status`                  | `'final' \| 'scheduled' \| 'cancelled'` | 中止は消化試合に数えない                                             |
| `venue`                   | `string`                                |                                                                      |
| `startTime`               | `string \| null`                        | 未実施試合のみ                                                       |

### 4-2. `TeamRecord`（試合ログから復元。永続化しない）

試合数・勝敗分・得失点に加えて、**リーグ戦のみの成績**（`leagueWins` ほか）と**対戦相手ごとの成績**（`h2h`）を持つ。後者2つは順位決定のタイブレークに必要。

### 4-3. `Snapshot`（`latest.json` / `snapshots/*.json`）

`src/lib/snapshot.ts` が型を定義する。スクリプトとページの唯一の契約点。球団ごとに順位・成績・実力推定値・マジック・敗退状況・各種確率・決定日分布を持つ。

## 6. 計算ロジック

### 6-1. 勝率と順位決定（`compare.ts`）

勝率 = **勝 ÷ (勝 + 負)**。引き分けは分母から除かれる。

| 順  | セ・リーグ                           | パ・リーグ             |
| --- | ------------------------------------ | ---------------------- |
| 1   | 勝率                                 | 勝率                   |
| 2   | **勝利数**                           | 当該球団間の対戦勝率   |
| 3   | 当該球団間の対戦勝率                 | リーグ内対戦成績の勝率 |
| 4   | リーグ内対戦成績（交流戦除く）の勝率 | 前年順位               |
| 5   | 前年順位                             | —                      |

2番目の基準が違うため、**まったく同じ成績でもリーグによって優勝球団が変わりうる**。この性質はテストで固定してある。

実装上の注意が2つある。

1. **勝率は割り算せず交差積で比較する。** 浮動小数の等価判定で同率を取りこぼさないため。
2. **「当該球団間」は並んでいる球団の集合に依存する。** 3球団が並べばその3球団の総当たり成績になる。したがって単純な二者比較のソートでは実装できず、上位条件で並んだ塊を段階的に細分化していく方式にしている（`refine()`）。

`compare.ts` 以外の場所にリーグ規定を書かない。ここがバグると全指標が同時に狂うので、テストを最も厚くしている。

### 6-2. マジックナンバー（`magic.ts`）

2つの値を出す。

- **慣用値**: `M = ライバルの最大到達勝利数 − 自チーム勝利数 + 1`。報道と同じ式。勝利数だけで計算するため、引き分け数が違う相手が絡むと実態とズレる。
- **厳密値**: 「残りのうち k 勝すれば他の結果に関わらず優勝が確定する」を満たす最小の k。自チームを最悪ケース（k勝して残りは全敗）に固定し、各ライバルの到達しうる最高成績と規定に沿って比較する。直接対決が残っていれば「自チームが勝つぶんライバルは勝てない」ことも織り込む。

点灯条件は NPB の慣例どおり「自チーム以外の全球団で自力優勝の可能性が消えたとき」。

**設計上のポイント（記録）**: 当初の計画ではマジックの計算にも最大流を使うつもりだったが、不要だと分かった。「ライバル j が自分を上回れるか」は j が単独で全勝すれば達成できるので、ライバル同士の潰し合いを考える必要がない。潰し合いの考慮が要るのは「j がリーグ1位になれるか」＝敗退判定のほうだけ。この整理のおかげで、シミュレーションの内側で毎日走る優勝確定判定が O(球団数) の単純比較で済み、20,000試行が200msで回る。

### 6-3. 数学的敗退（`elimination.ts`）

「自力優勝が不可能」と「数学的に敗退」は別物。自力優勝の判定はライバルが全員同時に勝ち続ける前提で見るが、実際にはライバル同士も潰し合うので全員が勝ち続けることはできない。

これを厳密に解くのが baseball elimination problem（Schwartz 1966）。ライバル同士の残り試合を「誰の許容勝ち数も超えないように配れるか」という**最大流／最小カット**の問題に変換する。

- source → ペアノード（ライバル j と k の残り h_jk 試合ぶんの容量）
- ペアノード → j, k（容量∞）
- j → sink（j が許容できる追加勝利数）

最大流がライバル同士の残り総試合数に届かなければ敗退。チーム数6なのでネットワークは極小で、Dinic 法の素朴な実装で十分。

### 6-4. 実力の推定（`strength.ts`）

1. ピタゴラス勝率 `得点^1.72 / (得点^1.72 + 失点^1.72)`。指数は MLB 慣用の 1.83 ではなく NPB により合う 1.72。
2. 実勝率と 50:50 でブレンド。
3. 平均への回帰。`.500 の相手と70試合戦った` ぶんの重みを足す。

1試合の勝敗確率は log5（Bill James）で求め、ホームアドバンテージをロジット空間のシフトとして加える。

**ホームアドバンテージと引き分け率は12球団をまとめて集計する。** リーグ別に分けると1リーグ約300試合しかなく標準誤差が3%近くになる。実際 2026年のパ・リーグは 58.3%（.500 から 2.9σ）だったが、これはほぼ標本誤差。ホームアドバンテージも延長規定もセ・パで違わないので、分ける理由がない。そのうえで長期水準（ホーム勝率 54%）へ縮小推定する。

### 6-5. 残り試合の導出（`schedule.ts`）

残り直接対決数は日程表の未消化カードを数えるのではなく、**`25 −（その相手との消化数）`** で導出する。日程表を数える方法だと、雨天中止でまだ再編成日が決まっていない試合を取りこぼすため。日程表に足りないぶんはシーズン最終盤に仮置きし、`confirmed: false` で区別する。

### 6-6. シミュレーション（`simulate.ts`）

日程は全試行で共通なので、日付ごとの「残り試合数」「残り直接対決数」は前処理で1度だけ作る。試行の中では結果だけが変わる。

各試行で日付順に試合を消化し、**その日を終えるたびに優勝確定を判定**して、確定した日を記録する。判定は 6-2 の単純比較で済むため安い。優勝が確定した球団は必ずその時点の勝率でも首位になっている（残り全敗しても他を上回るなら今の勝率も他以上）ので、上位2球団だけ調べれば足りる。

勝率が完全に並んで当該球団間の対戦成績で決着するケースは、数学的な確定としては最後まで立たない。この場合は実際に決着する最終日に計上し、その割合を `tiebreakDecidedRate` として別途表示する。

## 7. データ取得と検証

`https://npb.jp/games/<year>/schedule_MM_detail.html`（MM = 03〜11）をパースする。

- 各試合は `<tr id="dateMMDD">` の1行。`.team1` がホーム、`.team2` がビジター
- 確定試合は `.score1` / `.score2` に数字が入る。未実施は `&nbsp;`、中止は `.cancel` が付く
- オールスター（`セ・リーグ vs パ・リーグ`）は球団として解釈できないのでスキップし、件数を報告する

礼儀として1日1回・8リクエストのみ、`User-Agent` に用途と連絡先を明記、サイトに出典を表記している。`npb.jp/robots.txt` は 404（クロール制限の宣言なし）。

**検証（最重要）**: `scripts/verify-standings.ts` が、復元した順位表を [NPB 公式順位表](https://npb.jp/bis/2026/stats/) と機械的に照合する。試合数・勝敗分・**対戦相手ごとの成績**・交流戦成績まで比較し、1件でも食い違えば終了コード1で落ちる。GitHub Actions はこの検証を通ってからでないとデータをコミットしない。壊れたデータで上書きするより、前日の結果を出し続けるほうが害が小さい。

2026年9月3日時点で12球団すべてが完全一致することを確認済み。

**部分取得のマージ（記録）**: `--months` で一部の月だけ取り直せるようにしてあるが、当初の実装は取得した月だけで `games.json` を丸ごと上書きしていた。9月だけ取り直したときに894試合が151試合に消し飛んで気づいた。現在は取得した月ぶんだけを既存データから外して差し替え、それ以外の月はそのまま残す。毎日全8ページを取りに行くのは npb.jp に無駄な負荷をかけるので、いずれ「当月＋前月だけ取得」に切り替えたときに効いてくる。

### 7-1. 日々の更新

`npm run update` が `scrape → verify → snapshot` を順に実行する。`verify` が落ちれば `snapshot` は走らないので、壊れたデータが `latest.json` に入ることはない。

npb.jp への確定スコアの反映には**試合終了から数時間かかる**。9月4日 0:20（JST）の時点では9月3日の結果がまだ載っていなかった。GitHub Actions の cron を JST 01:00 に置いているのはこのためだが、それでも間に合わないことがある。**その日の試合を確実に取り込みたいなら翌朝以降に走らせる**のが安全。

## 8. 「もしも」シミュレーター

球団ごとに「残り全勝」「残り全敗」を指定すると、その条件で優勝確率を計算し直す。

- サイトの数字を作っているのと**同じ `src/engine`** を Web Worker で走らせる。ビルド時は Node、ここではブラウザ、という違いしかない
- 試合ログ全体（約900試合・152KB）を配るのは無駄なので、`SeasonSeed` という必要な数字だけの形（8KB）に落として配る
- 両チームに「全勝」を指定した直接対決のように指定が矛盾する試合は、どちらにも固定できないので確率に任せ、その件数を表示する

### 8-1. ワーカーへ渡す前にプロキシを剥がす（記録）

Svelte 5 は props や `$state` を**プロキシで包む**。プロキシは構造化複製アルゴリズムで複製できないため、`worker.postMessage(seed)` がそのまま `DataCloneError` で落ちる。初期化メッセージの送信自体が失敗し、その後の実行が「初期化されていない」で失敗する、という分かりにくい壊れ方をした。

送るのは数値・文字列・配列だけなので、`JSON.parse(JSON.stringify(message))` で素のオブジェクトに落としてから渡している（`send()`）。8KB のシードで一度だけなのでコストは無視できる。

### 8-2. 初期化の完了を待つ

あわせて、`init` の完了（`ready` 応答）をリーグごとに追跡し、完了前の実行要求は保留して `ready` 到着時に走らせるようにした。当初は「ワーカーへのメッセージは送信順に処理される」前提で `init` の直後に `run` を送っていたが、初期化が失敗しても実行が飛んでしまい、エラー表示が実行側のもので上書きされて原因が見えなくなっていた。順序の暗黙の前提に頼らないほうが、壊れたときに原因が分かる。

## 9. 非機能要件

- **JS 0KB**: シミュレーター以外の16ページは `<script>` タグを1つも出さない
- **横スクロール**: 幅の広い表とグラフは `.scroll-x` の中だけでスクロールさせ、ページ本体は横に溢れさせない
- **ライト/ダーク**: `prefers-color-scheme` でトークンを差し替える
- **再現性**: 乱数はシード固定。同じデータからは常に同じ結果が出る
- **性能**: 20,000試行 × 2リーグで約400ms（Node / ブラウザとも）

## 10. 既知の制限

- **敗退判定は引き分けが起きない前提。** 引き分けは勝率の分母から外れるため、ライバルにとっては敗けより有利に働く。つまり引き分けを許すと優勝確定はここでの判定よりわずかに遅くなりうる。この前提は報道のマジックナンバーと同じで、シミュレーション側では引き分けを確率的に発生させている
- **実力の推定はチーム単位。** 先発投手の並び、故障、移籍、消化試合の偏り、優勝決定後の主力温存は考慮していない
- **縮小推定の強さ（70試合）は実勝率に対して導かれた値**を、ピタゴラス勝率とのブレンドにもそのまま適用している。ブレンドのほうが分散が小さいぶん、わずかに過剰に縮小している可能性がある
- **中止で再編成日が未定の試合は最終盤に仮置き**している。決定日の予測はそのぶん後ろにずれうる
